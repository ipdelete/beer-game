Inspect AI & LiveBench — Implementation Patterns

How two more references handle the 8 improvement areas. Comparing against AgentBench to identify the best patterns to borrow.

Headline Findings

Inspect AI is the gold standard for observability, statistical rigor, metric extensibility, and caching. It beats AgentBench on every observability axis. LiveBench's signature contribution is the release-date gating mechanism — questions have livebench_release_date and livebench_removal_date fields and are filtered at load time. Surprisingly simple, surprisingly effective.

Inspect AI — Standout Patterns to Steal

1. EvalSpec manifest with full provenance

Every run captures: eval_set_id, run_id, task_version, task_args, model + generate config, dataset, scorers, metrics, sandbox config, packages, and git revision (type, origin, commit, dirty). All in one structured object. (src/inspect_ai/_eval/task/log.py:186-224, :66-72)

Why it matters: a result file can answer "what produced this number?" without referring to anything outside the file.

2. Telemetry baked into the model wrapper

ModelUsage tracks input_tokens, output_tokens, total_tokens, cache_read, cache_write, reasoning_tokens, total_cost. ModelOutput.time and ModelCall.time store per-call latency. record_and_check_model_usage() + emit_model_usage() fire after every generate. (src/inspect_ai/model/_model_output.py:14-41,161-166, _model.py:1175-1186)

Lesson: wrap the model client once, get telemetry everywhere for free. Don't sprinkle timing code in task implementations.

3. Epochs + reducers as a first-class concept

EvalConfig.epochs defaults to 1; epochs_reducer defaults to ["mean"]. Available reducers: mean, stderr, std, var, bootstrap_stderr, grouped. total_samples = dataset_samples × epochs. (src/inspect_ai/log/_log.py:62-87,694-703, scorer/_metrics/__init__.py)

Lesson: this is exactly the "k-run variance" pattern from our improvement plan, productized. Bootstrap stderr out of the box.

4. Metric registry via @metric decorator

@metric
def bullwhip_amplification():
    def compute(scores: list[SampleScore]) -> float: ...
    return compute

Registered via registry_add(metric, RegistryInfo(type="metric", name=...)). Referenced in logs as MetricSpec(metric=..., args=...). (src/inspect_ai/scorer/_metric.py:304-436)

Lesson: a custom metric is one decorated function. No core changes. This is the right pattern for our bullwhip / recovery-time / parse-rate metrics.

5. File-based response cache with composite key

Cache key includes: config, serialized input messages (excluding message id), base_url, tool_choice, tools, expiry, scopes, and optionally epoch. Stored under cache_path(model=...) / entry.key. (src/inspect_ai/model/_cache.py:139-171,196-243)

Lesson: response-level caching (not just sample-level) means re-scoring or re-aggregating doesn't re-query the model. Massive cost savings for local-model iteration. Per-epoch separation prevents accidental cross-epoch sharing.

LiveBench — Standout Patterns to Steal

1. Release-date gating (the big one)

Every question has livebench_release_date and optionally livebench_removal_date. load_questions() filters by the active release in LIVE_BENCH_RELEASES. Old questions are retired by setting their removal date. (common.py:74,177-235,225-231)

# Effectively:
questions = [q for q in all_questions
             if q.release_date <= active_release
             and (q.removal_date is None or q.removal_date > active_release)]

Why brilliant: contamination resistance without procedural generation. You just maintain a calendar of scenario releases and retirements. Versionable, reproducible (pin a release), and you can A/B test "did the model get better, or did the questions get harder?"

For us: tag each beer-game scenario with a release date. Pin active_release = "2026-Q1" for a given leaderboard. Add new scenarios over time. Retire ones that get memorized.

2. Multi-strategy parsing per task

Connections task tries <solution>...</solution>, then \boxed{}, then legacy bold format (connections/utils.py:48-103). Zebra puzzle tries the same plus a last-line fallback (zebra_puzzle/utils.py:60-87).

Lesson: the pattern is "try formats in order of preference; first match wins." For us this would be: strict integer parse → integer-in-last-line → first integer anywhere → JSON-mode field. Track which strategy succeeded so we can measure parse robustness per model.

3. Programmatic verification over LLM-as-judge

README quote: objective answers are used "without the use of an LLM judge." Scoring is dispatched per-task to deterministic functions (gen_ground_truth_judgment.py:91-205).

Lesson: matches our beer-game advantage. Don't drift toward LLM-as-judge unless absolutely necessary.

4. Variance checker as a separate utility

check_question_variance.py runs N iterations per model, counts variant answers/scores. It is not part of the main benchmark flow. (check_question_variance.py:15-16,195-247)

Lesson (anti-pattern): they treat variance as an afterthought, separate from the leaderboard. Inspect AI's "epochs are first-class" approach is materially better. Don't repeat LiveBench's split here.

5. YAML model configs

Models defined as livebench/model/model_configs/*.yaml, loaded via ModelConfig (api_model_config.py:8-37). Override at CLI with --api-base, --api-key, --max-tokens, --force-temperature, --num-choices.

Lesson: good shape for declarative model definitions — one YAML per model, CLI flags for run-time overrides. Combine with AgentBench's import/default/overwrite for the full picture.

Implication for Our Plan

The improvement plan stands and gets sharper:

  • The bullwhip metric becomes a one-decorator addition if we adopt the @metric pattern. Item 5 in the plan is small once items 1–2 are in place.
  • Procedural scenarios may be overkill at first. LiveBench shows you can buy most of the contamination-resistance win with release-date gating alone — much cheaper to implement. Procedural generation can be phase 2.
  • K-run variance is solved upstream. Don't reinvent epochs + reducers; that pattern is mature.
  • Response caching is more valuable than I previously credited. For local-model iteration on a slow box, caching individual LLM responses by composite key (not just completed games) saves hours.

Revised "First Sprint"

  1. SQLite schema with manifest, scenarios, games, decisions, states, metrics. Manifest captures git SHA, prompt version, scenario release.
  2. Wrap LLM client for telemetry — latency, tokens, context%, parse strategy. Borrow Inspect AI's ModelUsage shape.
  3. Release-date tagging on scenarios — even with one scenario today, structurally support release_date + removal_date. Borrow from LiveBench.
  4. Metric registry — even a tiny decorator-based one. Implement cost, bullwhip, recovery_time, parse_rate as the first four. Borrow from Inspect AI.
  5. Multi-strategy parser with ordered fallbacks, strategy tracking. Borrow from LiveBench.
  6. Then procedural scenarios, k-run epochs, response cache. These build on the foundation.
