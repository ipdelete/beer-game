What's Actually There

  • Core engine: BeerGameEngine in src/engine/simulation.py with 4 roles, two-phase weekly update (snapshot → decisions → execute → wire → record).
  • Two decision agents: Sterman anchor-and-adjust baseline (src/mechanistic/agent.py) and LLM-backed (src/gabm/agent.py) via OpenAI-compatible endpoint (Ollama, ds4, etc.).
  • Demand pattern: Single hardcoded step — 4 cases weeks 1–4, then 8 thereafter (src/roles/retailer.py:34-57).
  • Costs: $0.50/case/week inventory, $1.00/case/week backlog (src/roles/record_sheet.py:23-30).
  • Runner: scripts/tournament.sh iterates MODELS env var, writes per-model CSV + log + summary.tsv.
  • Output: CSV columns Turn, Role, Inventory, Backlog, Order, ShipmentReceived, TotalCost, IncomingOrder, OnOrder.
  • Tests: 3 test files covering engine, simulation, bullwhip behavior.
  • Docs: README, docs/benchmark-findings.md, leaderboard, methodology, limitations.

What's Genuinely Good ✓

  1. Mechanism transparency. No LLM-as-judge, no scoring ambiguity — total cost is mechanically computed by the simulator. This is a major scientific advantage over chat-arena-style benchmarks.
  2. Mechanistic baseline (Sterman) for reference. Lets you ask "is this LLM beating the published heuristic?" — that's a real, interpretable bar.
  3. Clean decision-fn contract. Callable[[PlayerView], int] is the right abstraction; trivially extensible.
  4. Drop-in model integration. OpenAI-compatible endpoint covers ~all relevant local serving stacks for free.
  5. Per-role, per-week traces. Strong basis for error analysis — you can see exactly where a model went off the rails.
  6. Real working tests covering engine correctness, demand step, bullwhip behavior, two-phase ordering.
  7. Lightweight infra. Beats AgentBench on time-to-first-run by an order of magnitude.

What's Concerning ✗

  1. Single scenario = severe contamination risk. The 4→8 step demand pattern is the canonical textbook example. Models almost certainly know it. Without procedurally generated demand, you cannot separate "good reasoning" from "memorized strategy."
  2. No variance reporting. Single run per model at temperature 0.4 is noise-amplified. Two re-runs may shuffle the leaderboard. This is a credibility issue for any conclusions drawn from the current results.
  3. No seed control. Reproducibility is at the mercy of the inference backend. A user can't re-run your published results and expect to match them.
  4. Bullwhip metric is plot-only, not in code. The most distinctive system-dynamics signal isn't a reportable number; it has to be eyeballed.
  5. Discriminative power untested. Do the 5 tested models actually play differently in ways that survive variance? Unknown.
  6. One prompt, one format. "Respond with ONLY a single non-negative integer" — some local models will sometimes break this format. Unclear how parse failures are handled or counted.
  7. No resume / caching across tournament runs. A crash mid-tournament re-runs everything.
  8. No structured config. Env vars + bash scripts. Fine for now; will bite when scenario count grows.
  9. "Tournament" is a misnomer. Models play independently against the same fixed environment — there's no head-to-head, no shared scoring frame beyond total cost.

The Honest Picture

The beer-game tool is a well-engineered single-scenario simulator with first-class local-model support. As a benchmark in the rigorous sense, it currently scores low on validity, reliability, and coverage — the three axes that decide whether a leaderboard can be trusted. The good news: every weakness is fixable without changing the core engine.

High-Leverage Improvements (Ranked)

  1. Procedural scenario generation. Parameterize demand (constant, step, ramp, sinusoidal, random, adversarial) and cost ratios. Generate 50–500 scenarios per benchmark run. Single biggest validity + contamination-resistance win.
  2. Variance reporting. Run each (model, scenario) k times (e.g., k=5), report mean + 95% CI. Without this no model comparison is defensible.
  3. Bullwhip as a first-class metric. Compute amplification ratio (std(factory_orders) / std(customer_demand)) per run, alongside cost. Add to summary TSV.
  4. Seed control. Pass seed to scenario generator and surface it in output. Reproducibility you can publish.
  5. Multiple decision-extraction strategies. Try strict integer parse, regex fallback, JSON-mode, structured outputs. Track parse-failure rate per model — that's itself a useful capability signal.
  6. Resume + caching. Hash (model, scenario, seed, prompt_version) → skip if result exists. Essential as scenario count grows.
  7. Difficulty calibration. Tag scenarios easy/medium/hard (e.g., by demand volatility). Report per-difficulty scores so the leaderboard has dimensionality.
  8. YAML config. Move from env vars to config.yaml defining models, scenarios, seeds, k. Future-proof.
  9. Position-isolation mode. Let the model play just one position with the other three as Sterman baselines — cleaner signal on individual decision quality.
  10. Statistical significance in the leaderboard. Don't show a ranking — show "model A beats model B at p < 0.05" via paired bootstrap over scenarios.

Recommendation

Don't abandon the project for a bigger framework. The core engine is sound, the model-integration story is excellent, and the mechanism transparency is a real scientific edge. Invest in scenario generation + variance + bullwhip metric (items 1–3 above) before anything else — those three changes alone would push the composite from ~2.5 to ~3.5 and make the leaderboard publishable.
