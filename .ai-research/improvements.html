1. Storage — Bundle Format

One run produces one bundle (directory or zip). Single artifact, multiple files inside.

runs/<run_id>.eval/
  manifest.json          # provenance: git_sha, prompt_version, scenario_release,
                         # config snapshot, model list, started_at
  scenarios.jsonl        # one line per scenario (id, demand, costs, weeks,
                         # release_date, removal_date, seed)
  games.jsonl            # one line per game (game_id, run_id, scenario_id,
                         # model, seed, epoch, total_cost, bullwhip, wall_s)
  decisions.parquet      # high-volume per-LLM-call telemetry (OTel attrs)
  states.parquet         # per (game, week, role): inventory, backlog, order,
                         # shipment, cost
  traces/                # optional full conversation logs
    <game_id>.jsonl
  report.html            # generated static report
Why this beats SQLite: queryable with DuckDB directly (SELECT * FROM 'runs/*.eval/games.jsonl'), Parquet handles the hot path (10k+ decisions per run), JSONL is human-readable and grep-able, bundle is one artifact to share.

2. Telemetry — OpenTelemetry GenAI Conventions

Architecture

LLM call
  └── OTel span (gen_ai.* + beergame.* attributes)
        ├── → Parquet writer  (custom span processor → decisions.parquet)
        └── → OTLP exporter   (optional; pipe to Jaeger/Tempo for debug)
Caveat: GenAI conventions are still status Development (not Stable) as of late 2025. Snapshot parsed values into stable column names you control in Parquet so a convention rename doesn't break historical data.

3. Release-Date Gating (Borrowed from LiveBench)

Each scenario carries:

{ "scenario_id": "step_4_8_50w",
  "demand_pattern": "step",
  "params": { "low": 4, "high": 8, "step_week": 5 },
  "release_date": "2026-Q1",
  "removal_date": null,
  "seed": 42 }

Runs pin active_release. load_scenarios() filters: release_date <= active AND (removal_date is null OR removal_date > active). Memorized scenarios get retired.

4. Metric Registry (Borrowed from Inspect AI)

@metric
def bullwhip_amplification():
    def compute(games: list[GameResult]) -> float:
        return std(game.factory_orders) / std(game.customer_demand)
    return compute

@metric
def parse_failure_rate():
    def compute(decisions: list[Decision]) -> float:
        return sum(1 for d in decisions if not d.parse_ok) / len(decisions)
    return compute

Metrics declare themselves at import. report.py discovers them via the registry. Adding a new metric never touches core code.

5. Multi-Strategy Parser (Borrowed from LiveBench)

STRATEGIES = [
    ("strict_int",         lambda s: int(s.strip())),
    ("last_line_int",      lambda s: int(re.search(r"\d+", s.splitlines()[-1]).group())),
    ("first_int_anywhere", lambda s: int(re.search(r"\d+", s).group())),
    ("json_field",         lambda s: int(json.loads(s)["order"])),
]
for name, parse in STRATEGIES:
    try: return parse(raw), name
    except Exception: continue
return None, "failed"

Track parse_strategy per call in decisions.parquet. Compute parse-failure rate per model as a capability signal.

What to Skip / Defer

  • SQLite — not how the field stores eval data.
  • Web dashboard — static HTML from the bundle is enough.
  • Distributed tracing backend — OTLP file exporter for archival; only run a Jaeger/Tempo if debugging a single weird run.
  • GPU utilization tracking — non-portable, not worth the engineering until requested.

Revised First Sprint

  1. Bundle writer. Define the JSON manifest schema, scenarios.jsonl shape, and Parquet schemas for decisions + states. Implement append-as-you-go writers.
  2. OTel-instrumented model client. Wrap the existing openai.OpenAI client. Emit spans following GenAI conventions, plus beergame.* attributes.
  3. Custom span processor → writes attributes to decisions.parquet on span end.
  4. Scenario release tagging. Add release_date / removal_date to scenario definitions and a load-time filter.
  5. Metric registry + first 4 metrics: cost, bullwhip, recovery_time, parse_rate.
  6. report.py consumes a bundle, queries via DuckDB, outputs static HTML report.

Everything else (k-run epochs, response cache, procedural scenarios, YAML config, significance testing) builds on this foundation.
